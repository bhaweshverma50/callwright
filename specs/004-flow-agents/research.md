# Research: Flow Agents

**Feature**: 004-flow-agents | **Date**: 2026-10-16 | **Plan**: [plan.md](./plan.md)

Each entry: Decision, Rationale, Alternatives considered. The reference product's behaviour
(research/calldash-functional-spec.md sections 2.3 to 2.9) is input, not a template.

## R1. Storing the graph

- **Decision**: One `flows` row per flow agent holding `graph` as JSONB (`nodes[]`, `edges[]`,
  `viewport`), a monotonically increasing `revision`, and `last_validation` (JSONB). Nodes and
  edges are not separate tables.
- **Rationale**: The graph is always read and written whole (canvas load, save, compile,
  assistant). Validation and compile run in Python over the whole document. A document fits the
  access pattern and keeps saves atomic. Size cap (200 nodes, 500 edges, about 1 MB) keeps it well
  inside Postgres limits.
- **Alternatives**: `flow_nodes` and `flow_edges` tables (rejected: every save becomes a diff of
  hundreds of rows, no query needs per-node SQL access, and published versions snapshot JSON
  anyway).

## R2. Optimistic concurrency on save

- **Decision**: `GET` returns `ETag: "<revision>"`; `PUT /v1/flows/{flow_id}` requires
  `If-Match`. A stale revision returns 412 `flow_revision_conflict` (problem+json) carrying the
  current revision. Each successful save increments `revision`.
- **Rationale**: Two tabs or the assistant plus a manual edit must not silently overwrite each
  other (spec US1 scenario 7). Standard HTTP semantics, trivial to implement.
- **Alternatives**: Last-write-wins as in the reference product (rejected: silent data loss);
  CRDT or live collaboration (rejected: no multi-user workspaces in v1, Principle VI).

## R3. Node and edge identifiers

- **Decision**: Node and edge ids are flow-local strings generated by the client:
  `n_<8 base32 chars>` and `e_<8 base32 chars>`, pattern `^[ne]_[a-z0-9]{8}$`. They are not
  platform entity ids and get no ULID prefix.
- **Rationale**: Nodes live inside one flow document; nothing references them across tenants.
  Short ids keep compiled configs and call events readable. Stable ids are required for diffs,
  version comparison and transitions recorded on calls.
- **Alternatives**: Timestamp ids like the reference product (rejected: collide when two nodes are
  added in the same millisecond by the assistant); global ULIDs (rejected: no need, longer).

## R4. Canvas and auto-layout

- **Decision**: `@xyflow/react` 12 with one custom node component per node type, `smoothstep`
  edges with closed arrow markers, and handles that encode edge triggers (webhook and transfer
  nodes show separate success and failure handles; rule conditions show one handle per rule plus
  "otherwise"). Auto-layout uses `@dagrejs/dagre` 1.x with `rankdir: LR`, `nodesep: 60`,
  `ranksep: 120`, `marginx/marginy: 32`, measured node sizes from React Flow, then `fitView`.
- **Rationale**: `@xyflow/react` is mandated by the constitution. dagre is synchronous, small
  (about 30 KB gzipped) and lays out 100 nodes in well under 100 ms, meeting SC-008.
- **Alternatives**: `elkjs` (rejected: about 1.3 MB, async web worker needed, better only for
  orthogonal edge routing we do not need); hand-rolled layered layout (rejected: reinventing).

## R5. Validation location

- **Decision**: Validation is implemented once, in Python (`services/api/app/flows/validation.py`).
  The client calls `POST /v1/flows/{flow_id}/validate` with the unsaved graph, debounced 600 ms
  after edits, and also gets the result back from every save. No TypeScript copy of the rules.
- **Rationale**: One source of truth; compile reuses the same pass. A full validation of a
  200-node graph is a few milliseconds plus a request round trip, fast enough for a debounced
  panel.
- **Alternatives**: Duplicate rules in TypeScript for instant feedback (rejected: drift risk,
  Principle VII contract tests would have to cover two implementations). Simple local checks
  (missing required text field) stay as ordinary form validation in node panels.

## R6. Validation algorithm

- **Decision**: Single pass building adjacency maps, then: start-node count, edge endpoint
  existence, per-type outgoing-trigger rules (table in data-model.md), BFS from Start for
  reachability, reverse BFS from End and Transfer nodes for "no way out" regions, transition name
  derivation and uniqueness, variable def/use analysis (variables set by Start dynamic variables,
  task schemas, extract fields, webhook mappings, plus built-ins), catalog and tool reference
  checks. Each issue: `{severity, code, message, node_id?, edge_id?, field?}`.
- **Rationale**: Linear in nodes plus edges; deterministic ordering of issues (by severity, then
  node order) so the UI and contract tests are stable.
- **Built-in variables** (never reported as unset): `call_id`, `direction`, `channel`,
  `from_number`, `to_number`, `timezone`, `current_time`, `current_date`, `current_datetime`,
  `agent_name`.

## R7. Transition naming

- **Decision**: Every edge leaving an agent or task node compiles to a function named
  `route_to_<slug>`, where `<slug>` is the edge label lowercased, non-alphanumerics collapsed to
  `_`, trimmed, max 48 characters. Users may set an explicit `function_name` override on the edge.
  Clashes inside one source node are validation errors (no automatic suffixes, so names stay
  predictable in transcripts). The prefix `route_to_` is reserved and rejected as a tool name by
  005.
- **Rationale**: Operators write labels as plain text ("Billing question") instead of the
  reference product's requirement to type a function name; the model still gets a meaningful,
  stable function name.
- **Alternatives**: Use the label verbatim as the function name (rejected: forces snake_case on
  users); numeric names (rejected: models choose worse with meaningless names).

## R8. Compiled flow format

- **Decision**: Our own versioned JSON, `compiled_flow.schema_version = 1`, produced by
  `services/api/app/flows/compiler.py` and validated by a Pydantic model shared as JSON Schema with
  the worker. Every node is fully resolved: persona prompt prepended to instructions, flow
  defaults merged with overrides into concrete `llm`, `tts`, `stt`, `language` blocks, tool ids
  replaced by full tool specs from `tools.service.resolve_for_snapshot` (secrets as references
  only), transitions as `{edge_id, function_name, description, target_node_id, trigger}`. The
  worker never needs the draft, the tool table or the catalog to run a call. Full shape in
  data-model.md.
- **Rationale**: Principle I: the runtime reads plain versioned data and never mutates it.
  Self-contained snapshots make replays and simulations (008) exact.
- **Alternatives**: Compile in the worker at call start (rejected: compile errors would surface
  mid-call, adds start latency, makes versions non-reproducible if catalogs change).

## R9. Where the compiled flow lives

- **Decision**: On publish, `flows.service.publish()` validates, compiles, then calls
  `agent_versions.service.create_version(agent_id, config, release_notes)` (002) with the agent's
  draft config extended by `flow: {flow_id, graph, graph_hash, compiled}`. `graph_hash` is SHA-256
  of the canonical graph JSON with positions and viewport removed, so layout-only changes do not
  register as flow changes in version diffs.
- **Rationale**: The spec requires the compiled form to be stored with the agent version.
  Embedding the source graph lets version history show node-level diffs and restore drafts.
- **Alternatives**: A separate `compiled_flows` table referenced by id (rejected: a second
  immutable store to keep consistent with versions).

## R10. Runtime executor design

- **Decision**: `services/voice-worker/worker/flow/` implements a state machine on LiveKit Agents
  (Python) 1.x. Each conversational node (agent, task) becomes an `Agent` instance with its own
  instructions, tools and optional per-node `llm`, `tts`, `stt` built through the existing adapter
  factories (003). Transitions are function tools generated from the compiled transitions; calling
  one returns the next node's handler, using the framework's agent handoff. Non-conversational
  nodes (say, condition, extract_variable, webhook, transfer, end) run inside the executor between
  handoffs through a `NodeHandler` registry keyed by `node_type` (the extension point). 003's
  `pipeline.py` delegates to `flow.executor.FlowExecutor` when `config.type == "flow"`.
- **Rationale**: The handoff pattern is native to the framework the constitution mandates, so
  per-node models and voices need no custom session plumbing. A handler registry lets new node
  types be added without touching the executor core.
- **Alternatives**: A single agent with a rewritten system prompt per node (rejected: cannot
  switch voice or STT per node, tools leak across nodes); an external workflow engine (rejected:
  Principle VI and hot-path latency).

## R11. Condition nodes at runtime

- **Decision**: `classify` makes one non-streaming model call with structured output whose schema
  is an enum of the category names, temperature 0, using the flow default model, timeout 1500 ms.
  On timeout or invalid output the first category is followed and the transition is recorded with
  trigger `fallback`. `rule` is evaluated by a small safe evaluator (no `eval`): operators
  `equals`, `not_equals`, `contains`, `matches` (Python `re.fullmatch`, 50 ms guard), `exists`,
  `gt`, `lt`; numeric comparison when both sides parse as numbers; rules checked in `sort_order`,
  then `else`.
- **Rationale**: Classification as one constrained call is faster and more reliable than letting
  the conversational model choose among tools; rules need no model at all.
- **Alternatives**: Treat categories as tool calls like the reference product (rejected: requires
  a conversational turn and can produce speech).

## R12. Context strategies

- **Decision**: `inherit` passes the full chat context to the next node. `reset` passes only the
  system prompt and a short "known facts" block of captured variables. `summarize` passes a
  running summary maintained in the background: after each completed agent turn the executor
  schedules a summary update (flow default model, max 150 tokens) that never blocks speech; at
  handoff the latest finished summary plus the last 2 turns is used. If no summary is ready, the
  last 6 turns are passed.
- **Rationale**: Summarizing at handoff time would put a model call on the hot path (Principle II).
  Background summaries cost tokens, which are metered on the call as normal LLM usage (Principle
  III).
- **Alternatives**: Summarize synchronously at handoff (rejected: 400 to 900 ms audible gap).

## R13. Transition latency

- **Decision**: Transition functions take no parameters (short tool-call payloads stream fast).
  When the target node has an entry line (`begin_message`), it is sent to TTS immediately on
  handoff while the new node's model starts in parallel only after the caller's next turn. When it
  has none, the new node generates the reply (one extra model call, reported separately in
  per-turn metrics as `transition_llm_ms`). The builder shows a hint on conversational nodes
  without an entry line.
- **Benchmarks**: Executor overhead per move (from tool call completion to the next audio request
  or next model request) target p95 at most 150 ms; measured by the offline harness with stubbed
  adapters so only executor time is counted (benchmark tasks in tasks.md, User Story 3).
- **Rationale**: Principle II requires a stated latency impact and a regression benchmark.

## R14. Recording transitions

- **Decision**: The worker posts CallEvents of kind `flow_transition` (and `flow_node_entered`) to
  `POST /v1/internal/calls/{call_id}/events` (owned by 003). The flows module defines the payload
  schema and serves `GET /v1/calls/{call_id}/flow-transitions` as a read projection over
  `call_events` filtered by kind. Live highlight uses the LiveKit data channel topic
  `callwright.flow` with messages `{type: "node_entered", node_id, at_ms}`.
- **Rationale**: Architecture section 5 lists flow transitions as CallEvent content. No new table
  (Principle VI). A partial index on `call_events (call_id, seq) WHERE kind = 'flow_transition'`
  keeps the read cheap.
- **Alternatives**: Dedicated `flow_transitions` table (rejected for v1; revisit if 007 per-node
  scorecards need heavier aggregation).

## R15. Creating a flow agent

- **Decision**: `POST /v1/flows` with `{name, language}` creates the Agent (type `flow`, via
  `agents.service.create_agent`) and the Flow with the starter graph in one transaction, returning
  both ids. Seeded defaults come from 002's language-defaults catalog
  (`llms`/`voices` modules); when a language has no entry, the `en-US` defaults are used and a
  warning is returned. Expected defaults (owned by 002, listed here for test fixtures): English
  variants use STT `deepgram/nova-3` and TTS `elevenlabs/eleven_flash_v2_5`; other European and
  Asian languages use STT `deepgram/nova-2` and TTS `elevenlabs/eleven_multilingual_v2`; Indic
  languages use STT `sarvam/saarika:v2.5` and TTS `sarvam/bulbul:v2`.
- **Rationale**: One request avoids an orphan agent with no flow (the reference product made three
  sequential calls). The starter graph (Start, Agent "Conversation", End with edge "Caller is
  done") validates cleanly, meeting SC-001.

## R16. Draft test calls

- **Decision**: The builder's Test tab asks 003 for a web test session with `use_draft: true`.
  003 calls `flows.service.compile_draft(agent_id)` which returns a compiled config or the
  validation errors; 003 then runs it as an unpublished test snapshot. This feature exposes the
  compile function; 003 owns the session endpoint.
- **Rationale**: Operators must test before publishing (US3 scenario 7) without creating a
  version per test.

## R17. AI flow assistant

- **Decision**: `POST /v1/flows/{flow_id}/assistant` with `{messages[], base_revision, graph?}`
  (graph defaults to the saved draft; the client sends its unsaved graph when dirty). The API
  calls the LLM adapter with a JSON-schema constrained response
  `{message, flow_name?, operations[]}` limited to the operation types in FR-036, with node config
  schemas that exclude model and provider overrides. The server then remaps temporary ids
  (`tmp_*`) to real `n_`/`e_` ids, applies the operations to an in-memory copy, validates it, and
  returns `{message, operations, proposed_graph, issues, base_revision}`. Approval happens on the
  client, which applies `proposed_graph` and saves with `If-Match: base_revision`. Model is the
  platform setting `FLOW_ASSISTANT_MODEL` resolved through the LLM catalog. Timeout 60 s. Charged
  through `billing.charge_feature(workspace_id, "flow_assistant", usage)` per request, including
  failed-but-completed model calls; nothing charged on timeout before the model returns.
- **Rationale**: Server-side remap and validation remove client complexity and let the proposal
  show its resulting errors before approval (FR-037). Excluding model overrides from the schema
  enforces FR-038 structurally rather than by stripping.
- **Alternatives**: Streamed operations applied live (rejected: hard to decline cleanly);
  assistant writes the draft directly (rejected: violates review-before-apply).

## R18. Limits

- Nodes 200, edges 500, instructions 16,000 characters per node, persona prompt 32,000
  characters, edge condition 1,000 characters, categories 20 per classify node, rules 20 per rule
  node, task schema 30 fields, extract fields 30, assistant messages 50 per request.
